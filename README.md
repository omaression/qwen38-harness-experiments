# qwen38-harness-experiments

[![CI](https://github.com/omaression/qwen38-harness-experiments/actions/workflows/ci.yml/badge.svg)](https://github.com/omaression/qwen38-harness-experiments/actions/workflows/ci.yml)

An evaluation harness for an LLM feature, with CI regression testing. It was built as a project for
an AI class.

The harness scores an **LLM bug-fix assistant** on a suite of tasks with hidden tests. It compares
a candidate (a new prompt, model or sampling setting) with the current baseline on the same items,
and decides by a written, tested rule whether the candidate may replace it. On every push to `main`
and every pull request, GitHub Actions makes that decision by replaying recorded model responses
("cassettes"), and fails the build when the candidate regresses. In the same run it gates a
deliberately regressed candidate and checks that the gate rejects it, so a change to the harness
that would let a bad model through also fails the build. A second feature, an **LLM
patch-correctness judge**, shows how to evaluate a classifier-style LLM feature against labels
that come from running tests.

- The harness uses only the Python standard library (3.10 or later). The tests need `pytest`.
- CI calls no model: it needs no GPU, no API key and no network, and the same cassettes always give
  byte-identical reports.
- A manual workflow job records and gates a live OpenAI-compatible endpoint when repository
  secrets configure one.

> **The demo data is synthetic.** The 34 tasks in `tasks/demo` were written for this repository
> and are not taken from any dataset or code base. The three cassette sets in `cassettes/` were
> generated by `scripts/make_demo_cassettes.py`, not produced by a model. They show how the harness
> decides. They say nothing about how good any model is. Every report says so per arm, and the CI
> summary opens with a banner saying so.

The full specification (architecture, data model, metric formulas, the gate rule, the ledger, CI) is
in [docs/DESIGN.md](docs/DESIGN.md). The module docstrings in `src/llm_eval_harness/` hold the same
contracts in more detail.

## The feature under test

**`bugfix`.** The model is given a buggy Python function, its docstring, and one test that fails on
it. It answers with an optional `<think>...</think>` block followed by exactly one JSON object:

```json
{"explanation": "max() was given lo twice; the upper bound is hi.",
 "patched_code": "def clamp(x, lo, hi):\n    ...\n    return max(lo, min(x, hi))\n"}
```

A product would apply `patched_code` directly, so the harness scores what the product would get. The
model never sees the task's hidden tests, its reference fix or its wrong fix. Prompts are versioned
templates (`bugfix/v1`, `bugfix/v2` in `src/llm_eval_harness/prompts.py`). A published template never
changes: a new prompt is a new version.

**`judge`.** The model is shown a task and a proposed patch and answers `{"verdict": true | false}`:
does the patch fix the bug? Each task gives two items: its reference fix (label `true`) and a
plausible wrong fix that passes the shown test but fails a hidden one (label `false`). The labels
come from running the tests, never from another model.

## Quick start

```bash
python -m pip install -e ".[test]"   # Python 3.10+; the harness itself needs only the standard library
python -m pytest -q                  # unit and end-to-end tests
llm-eval tasks validate --suite tasks/demo   # run every task's code in the sandbox, check for leakage
llm-eval tasks split                         # which tasks are dev and which are held out

# replay one arm on the dev split (iterate here: it does not spend the held-out split)
llm-eval run --feature bugfix --cassettes cassettes/candidate --split dev

# the gate CI runs: the candidate against the ledger's current baseline, on the held-out split
llm-eval gate --feature bugfix --candidate cassettes/candidate --baseline @current > report.json
jq '{promote, failed: [.gates[] | select(.enforced and (.passed | not)) | .gate]}' report.json
llm-eval summary report.json         # the markdown CI writes to the job summary
```

Without installing, run `PYTHONPATH=src python -m llm_eval_harness ...` from the repository root.
`jq` is used only to query reports. The workflow tests run the CI scripts with `bash` and `jq`, and
skip those checks when either is missing.

## How a reply is scored

A `bugfix` reply is checked in this order:

1. **Thinking.** If there is a `<think>` block (or thinking the server returned separately), it
   must be closed and between 1 and 1,200 words.
2. **Schema.** The answer must be exactly one JSON object with the two keys, each a non-blank
   string. Prose around it, a code fence, a missing or extra key, or a reply truncated at
   `max_tokens` makes the reply invalid. A lenient parse is recorded as a diagnostic only.
3. **Static scan.** An AST-based scan looks for unsafe constructs the patch added. Six block-class
   rules cover `eval`/`exec`, `os.system` and friends, `shell=True`, unsafe deserialisation
   (`pickle.loads`, ...), process control (`os._exit`, `signal.alarm`, ...) and interpreter
   tampering (`sys.settrace`, writes into `builtins`). Six flag-class rules (subprocess, dynamic
   import, file writes, network, introspection, `sys.exit`) are counted and decide nothing. Code
   with a block-class finding is never run.
4. **Execution.** The patch runs in a sandbox against the shown test and the hidden tests. The
   tests are stored as data (a call and the literal it must return, or the exception it must
   raise). The child process only reports what each call returned, and the parent compares. An
   exit status of 0 is never a pass by itself, and a missing result is a failure.

An item is **resolved** when the schema is valid, no block-class finding was added, and every shown
and hidden test passed. A patch that special-cases the shown input passes the shown test and fails
a hidden one: it is not resolved, and it is counted as an **overfit**.

A `judge` reply's prediction is the `verdict` of a schema-valid reply. A reply without one is wrong
for either label. No code runs.

## Metrics

Each arm (one cassette set, on one feature and split) gets these metrics. `resolved_rate`,
`schema_validity`, `tpr` and `tnr` come with a Wilson 95% interval (`*_ci95`), which stays inside
[0, 1] and does not collapse on small suites:

| Feature | Metric | Definition |
|---|---|---|
| bugfix | `resolved_rate` (primary) | resolved items / items |
| bugfix | `overfit_rate` | items that passed the shown test and failed a hidden one / items that passed the shown test |
| bugfix | `shown_pass_rate`, `hidden_pass_rate` | items whose shown (hidden) tests all passed / items |
| bugfix | `sast` | per rule, the items whose reply added a block or flag finding |
| bugfix | `by_tag` | items and resolved items per bug class (`off-by-one`, `boundary`, ...) |
| judge | `balanced_accuracy` (primary) | (TPR + TNR) / 2 over tasks with both items, with a bootstrap interval over tasks. A judge that ignores the patch scores exactly 0.5 |
| judge | `tpr`, `tnr`, `accuracy`, `precision`, `f1`, `approve_rate`, `confusion` | the usual classifier metrics; a reply without a valid verdict counts against its class |
| judge | `vs_chance` | whether the balanced-accuracy interval lies above 0.5 |
| both | `schema_validity`, `think_validity`, `lenient_only_rate` | the share of replies with a strictly valid answer, valid thinking, or an answer valid only under the lenient parse |
| both | cost | `completion_tokens_total`, `completion_tokens_mean`, `latency_median_s`, `finish_reasons` |

The gate compares the two arms **paired**, on the same item ids. Most of the variation between items
(some tasks are just hard) cancels out, and only the items where the arms disagree carry
information:

| Quantity | Meaning |
|---|---|
| `gains`, `losses` | items only the candidate got right, and items only the baseline got right |
| `delta` | primary(candidate) - primary(baseline) on the joined items |
| `ci95` | paired bootstrap 95% interval of `delta`: 2,000 seeded draws of task clusters (a task's two judge items, and twin tasks, are drawn together) |
| `mcnemar_p` | exact two-sided McNemar test of the losses against the gains |
| `mde80` | (1.96 + 0.84) times the bootstrap standard error of `delta`: the smallest true change a two-sided 5% test on this suite would detect four times in five |
| `min_significant_losses` | the fewest losses, with no gains, that McNemar calls significant: 6 at alpha 0.05, whatever the suite size |

## The gate rule

Rule `noninferior/1` promotes a candidate only when every gate that applies passes:

| Gate | Passes when |
|---|---|
| `schema_validity` | the candidate's schema validity is at least 0.95 |
| `think_validity` | the candidate's think validity is at least 0.90 |
| `new_sast_violations` | the candidate added no block-class finding that the baseline's reply to the same item does not have (bugfix only) |
| `primary` | `delta >= -margin`. The margin is 0 by default, so an exact tie passes; `--tie fail` makes it `delta > -margin` |
| `regression_test` | McNemar does not find a significant regression (losses > gains with p < alpha) |
| `gain_test` | only with `--require-gain`: a significant improvement (gains > losses with p < alpha) |

A tie is a decision, so the rule names it. The default passes ties because a regression test should
not block a refactor that changes nothing. Replacing a baseline because a change *helps* should
demand more: `--tie fail --require-gain`. A positive `--margin` (say 0.02) absorbs the noise of a
live, non-deterministic endpoint.

The gate decides on the point estimate, with McNemar as a second guard, because on a suite of a few
dozen items the 95% interval of the delta is wider than any margin worth setting. Every report
therefore carries the interval, `mde80` and `min_significant_losses`, so a reader can see how much
a decision is worth. Without a baseline (`--baseline none`), the primary metric is compared with a
floor (bugfix 0.5, judge 0.7, or `--floor`).

The gate refuses to compare arms that were not scored on the same items, the same suite and the same
split, and refuses recordings that do not answer today's requests: an unpaired comparison would
compare different questions.

`llm-eval gate` prints only the JSON report on stdout. Its exit status says whether the evaluation
ran, not what it decided:

| Exit | Meaning |
|---|---|
| 0 | The evaluation ran and the report was printed, whatever the verdict |
| 1 | It could not run or finish (endpoint, sandbox, I/O) |
| 2 | A usage error or a refusal: arms not scored on the same items, recordings that do not match today's requests, `@current` when the ledger names no baseline |

CI therefore reads the verdict from the report (`jq -e '.promote == true'`), and "the gate said no"
stays distinguishable from "the gate could not run".

## CI regression testing

`.github/workflows/ci.yml` has read-only permissions and five jobs:

| Job | When | What it does |
|---|---|---|
| `tests` | every push to `main`, every pull request | On Python 3.10, 3.11 and 3.12: `pytest`, `llm-eval tasks validate`, `llm-eval ledger verify` |
| `regression-gate` | after `tests` | Replays the cassettes (no secrets, no model calls). Gates `cassettes/candidate` and `cassettes/candidate-regressed` against the current baseline for both features, writes the job summary, uploads the reports, then enforces the verdicts |
| `experiments` | after `tests` | Replays every experiment's recorded real-model cassettes and fails when the current harness does not reproduce its committed reports in `experiments/*/expected/` byte for byte |
| `live-config` | manual dispatch only | Checks whether repository secrets configure a live endpoint; if not, the live job is skipped with a notice |
| `live-eval` | manual dispatch, when configured | Records the candidate and the baseline from a live endpoint, gates them, writes the summary and uploads everything |

The `regression-gate` job enforces two things:

1. **The candidate must promote.** `jq -e '.promote == true'` must hold on both candidate reports.
2. **The gate's self-test.** Both regressed reports must say `promote: false`, and must fail at
   least the expected gates: `primary`, `schema_validity` and `new_sast_violations` for bugfix, and
   `primary` and `schema_validity` for the judge. A harness change that lets a clearly regressed
   candidate through fails the build, even though the candidate itself still passes.

`ledger verify` in the `tests` job also re-fingerprints each feature's current baseline, so a
baseline recording edited outside the ledger fails the build.

### Reproduce CI locally

These are the `regression-gate` job's commands; run them from the repository root after the quick
start's install:

```bash
mkdir -p reports
for f in bugfix judge; do
  llm-eval gate --feature "$f" --split heldout --candidate cassettes/candidate --baseline @current \
    --items-out reports/items/candidate > "reports/$f-candidate.json"
  llm-eval gate --feature "$f" --split heldout --candidate cassettes/candidate-regressed --baseline @current \
    --items-out reports/items/regressed > "reports/$f-regressed.json"
done
llm-eval summary reports/bugfix-candidate.json reports/judge-candidate.json \
  reports/bugfix-regressed.json reports/judge-regressed.json > reports/summary.md
jq -c '{feature, candidate: .candidate.name, promote,
        failed: [.gates[] | select(.enforced and (.passed | not)) | .gate]}' reports/*-*.json
```

The last command prints:

```text
{"feature":"bugfix","candidate":"candidate","promote":true,"failed":[]}
{"feature":"bugfix","candidate":"candidate-regressed","promote":false,"failed":["schema_validity","new_sast_violations","primary"]}
{"feature":"judge","candidate":"candidate","promote":true,"failed":[]}
{"feature":"judge","candidate":"candidate-regressed","promote":false,"failed":["schema_validity","primary"]}
```

### What the self-test catches

Each row below is a change made to a fresh checkout, followed by a run of the `regression-gate`
job's steps exactly as the runner executes them (`bash --noprofile --norc -eo pipefail`, with the
`if:` conditions). The first row is the committed tree.

| Change | Gate step | Enforce the candidate | Self-test | Job |
|---|---|---|---|---|
| none | passes | passes | passes | **passes** |
| `cassettes/candidate-regressed` replaced by a copy of the candidate | passes | passes | fails: the regressed bugfix and judge candidates were promoted | **fails** |
| the schema bound lowered from 0.95 to 0.5 in `GateConfig` | passes | passes | fails: both regressed candidates are rejected, but no longer by `schema_validity` | **fails** |
| the SAST resolver blind to the builtin `eval` | passes | passes | fails: the regressed bugfix candidate no longer fails `new_sast_violations` (its `eval()` patch now runs, and passes the tests) | **fails** |
| the default margin raised from 0 to 1 | passes | passes | fails: `primary` no longer fails for either regressed candidate | **fails** |
| `cassettes/candidate` replaced by the regressed candidate | passes | fails: the bugfix candidate failed the gate | skipped | **fails** |
| one candidate recording's request hash changed | fails (exit 2: the recording answers another request) | skipped | skipped | **fails** |

The job summary and the reports are written and uploaded whether or not a step failed. In the
`tests` job, editing one reply in `cassettes/baseline` makes `llm-eval ledger verify` fail with
"the current baseline cassettes/baseline was changed outside the ledger".

### The demo results

These are held-out numbers: 21 tasks, 21 bugfix items and 42 judge items. Every arm is synthetic.
`[a, b]` is the 95% paired bootstrap interval of the delta.

| Feature | Arm (model, prompt) | Primary metric | Delta vs baseline | Gains / losses | McNemar p | Verdict | Failed gates |
|---|---|---|---|---|---|---|---|
| bugfix | baseline (demo-model-a, bugfix/v1) | resolved 14/21 = 0.667 | | | | current baseline | |
| bugfix | candidate (demo-model-a, bugfix/v2) | resolved 17/21 = 0.810 | +0.143 [-0.045, +0.350] | 4 / 1 | 0.375 | PROMOTE | none |
| bugfix | candidate-regressed (demo-model-small, bugfix/v2) | resolved 10/21 = 0.476 | -0.190 [-0.391, +0.000] | 0 / 4 | 0.125 | REJECT | primary, schema_validity (0.762), new_sast_violations (1) |
| judge | baseline (demo-model-a, judge/v1) | balanced accuracy 0.571 | | | | current baseline | |
| judge | candidate (demo-model-a, judge/v2) | balanced accuracy 0.881 | +0.310 [+0.175, +0.429] | 15 / 2 | 0.0023 | PROMOTE | none |
| judge | candidate-regressed (demo-model-small, judge/v2) | balanced accuracy 0.429 | -0.143 [-0.350, +0.048] | 6 / 12 | 0.238 | REJECT | primary, schema_validity (0.905) |

What the numbers show:

- **The v1 baseline overfits.** 7 of its 21 patches pass the shown test and fail a hidden one.
  The v2 prompt adds the rules "Make the function correct for every input its docstring
  describes, not only for the test you are shown" and "Never special-case the inputs of a test".
  It fixes 4 of those 7 and breaks 1 patch that v1 had right.
- **A promotion is not proof of a gain.** The bugfix candidate promotes because it is not worse,
  not because the improvement is significant: McNemar p is 0.375 and the interval includes 0.
  With `--tie fail --require-gain` the gate rejects it on `gain_test`, while the judge candidate
  (p = 0.0023) still promotes.
- **Small suites detect only large regressions.** McNemar needs at least 6 losses and no gains
  before it calls a regression significant. The regressed bugfix candidate's 4 losses are not
  significant (p = 0.125). It is rejected by the point estimate (`primary`), by its broken replies
  (5 of 21 not schema-valid, 2 of them valid only under a lenient parse; one truncated at
  `max_tokens`), and by the `eval()` it wrote for `evaluate-sum`, a new block-class SAST finding.
  That patch is never executed.
- **Judges can look fine and be useless.** The baseline judge approves 39 of 42 patches. Its
  balanced accuracy of 0.571 has an interval of [0.500, 0.650]. The report flags it as a rubber
  stamp that cannot be told apart from chance. The regressed judge is worse than the baseline
  (0.429) and breaks its format on 4 of 42 replies.
- **Cost is reported, not gated.** The judge candidate uses 5.0 times the baseline's completion
  tokens, because it thinks before answering and the rubber stamp does not. The report warns, and
  the decision is left to the reader.

On the dev split (13 tasks), the verdicts are the same. bugfix resolved: baseline 9/13, candidate
10/13, regressed 4/13 (3 `eval()` patches). Judge balanced accuracy: baseline 0.577, candidate
0.846, regressed 0.423. `tests/test_demo.py` pins these numbers.

### The live job

Run it from the Actions tab ("Run workflow") with a feature and a split. The split defaults to
`dev`, so that a live experiment does not spend the held-out split. It needs three repository
secrets: `LLM_EVAL_BASE_URL` (an OpenAI-compatible `/v1` URL), `LLM_EVAL_API_KEY` and
`LLM_EVAL_CANDIDATE_MODEL`. An optional fourth, `LLM_EVAL_BASELINE_MODEL`, sets the baseline model;
without it the baseline uses the candidate model, which measures a prompt change alone.

The job records the candidate with the current prompt, and the baseline with the prompt and
settings of the ledger's current baseline. It then gates the two recordings. Secrets and inputs
reach the scripts only as environment variables, and the job commits nothing. Its uploaded
artifacts hold the model's replies and the model names. In a public repository, other users may
be able to download them.

## Experiments on a real model

`experiments/` holds recorded replies of real open-weight models, for model-side changes put through the gate. Each experiment's README gives its setup, results and how to replay it.

- `experiments/exp-a-qwen38/`: Qwen3.8-27B with LoRA adapters, served by vLLM, on the demo suite. It compares an identity (no-op) adapter for `bugfix` and a trained judge adapter for `judge` against the base model.
  - The no-op adapter is rejected on one noisy item (McNemar p = 1.0).
  - The trained judge gains 15 points on the dev split, but cannot show it on a held-out split where the base model is already perfect.
- `experiments/exp-c-bonsai/`: Ternary Bonsai 2 27B (a ternary model, `Q2_0` GGUF on llama.cpp) against the stock bf16 Qwen3.8-27B on vLLM, on the HumanEvalFix suite. A Q8_0 arm on llama.cpp is the engine control, and a second recording of the bf16 arm is the no-op.
  - On the 74 held-out bug-fix tasks, the ternary model resolves 71 against bf16's 73 (−0.027, 2 losses, McNemar p = 0.5): about 97% of the bf16 rate. Against the Q8_0 arm it is −0.041 (3 losses, p = 0.25).
  - The engine change alone loses no bug-fix item. The no-op ties at 0.986 on the held-out bug fix (1 gain, 1 loss), and the gate at margin 0 rejects it on both dev splits.
  - The ternary model uses 1.6 times bf16's completion tokens on the held-out bug fix, and is the only arm with replies cut at the token limit.
  - No comparison is significant. The ternary model's losses are the size of the noise floor, and a margin near 0.05 would be the defensible setting for this suite.
- `experiments/exp-c-bonsai-demo/`: the same arms on the demo suite, where every arm is at or near ceiling. All three resolve every bug-fix item, and the gate's three rejections are single format failures on the judge.

Reports are named `<candidate>--vs--<baseline>.<feature>-<split>.json` (Experiment A's keep `<feature>-<split>.json`), and an experiment's `SUITE` file names its suite (default `demo`). The CI job `experiments` replays all 32 reports and fails when the current harness no longer reproduces any of them byte for byte.

## Writing the report

The class deliverable is an IEEE-format project report on the harness and its experiments.

- [docs/report/](docs/report/README.md) holds its text, one markdown file per section (abstract, I. Introduction to VII. Conclusion, references). Its README maps each section to the files and reports its claims rest on.
- [docs/paper/](docs/paper/) holds the same text as an IEEEtran conference paper (`main.tex`), with its bibliography (`refs.bib`) and generated tables (`tables/`). Build it from that directory with `pdflatex main && bibtex main && pdflatex main && pdflatex main`. It needs the IEEEtran class (`kpsewhich IEEEtran.cls`; see [docs/report/README.md](docs/report/README.md)).
- The result tables are generated from the committed reports by `python scripts/make_report_tables.py`, which writes `docs/report/tables.md`, `docs/paper/tables/*.tex` and the marked blocks of the results section. `tests/test_report_tables.py` fails when a table no longer matches the reports, so rerun the script after a report changes.
- Experiment C's tables (one gate row per comparison, with its token cost; one row per arm) are generated from `experiments/exp-c-bonsai/expected/` and `experiments/exp-c-bonsai-demo/expected/` in the same way.

## How to read a report

`llm-eval gate` prints one JSON object (`llm_eval_harness.report/1`):

| Key | What it holds |
|---|---|
| `promote` | The verdict CI reads. It is true only when every enforced gate passed |
| `gates` | One entry per gate: `value`, `op`, `bound`, `passed`, `enforced` and details. For example, `new_sast_violations` lists `{"item", "rule"}` pairs, and `primary` has `candidate`, `baseline` and `margin` |
| `comparison` | The paired comparison on the joined items: `n`, `gains`, `losses`, `delta`, `ci95`, `mcnemar_p`, `mde80`, `min_significant_losses` |
| `candidate`, `baseline` | Each arm's model, prompt id and prompt sha256, cassette fingerprint, `synthetic` flag, and all its metrics |
| `suite` | The suite's name and sha256, the sha256 of the split's task list, and counts |
| `warnings` | Why the decision may be worth less than it looks: synthetic arms, a small suite, a spent held-out split, a rubber-stamp or chance-level judge, a prompt that is not the current one, a cost increase |
| `provenance` | The harness version, the SAST rule-set fingerprint, the execution rule (`values/1`) and the feature's current prompt id |

The report has no time stamps or absolute paths, so replaying the same cassettes gives
byte-identical output. Two handy queries:

```bash
jq '[.gates[] | select(.enforced and (.passed | not)) | .gate]' report.json   # what failed
jq '.comparison | {delta, ci95, gains, losses, mcnemar_p}' report.json         # how sure
```

With `--items-out DIR`, the gate also writes one scored row per item and arm
(`DIR/<feature>.candidate.items.jsonl` and `DIR/<feature>.baseline.items.jsonl`). Each row has a
`problems` list that explains it. Three rows of the regressed bugfix candidate in CI's
`reports/items/regressed`:

```text
bugfix:apply-discount   exec: hidden test 1 failed: got 55.0, expected 45.0
                        exec: hidden test 2 failed: got 22.99, expected 16.99
                        exec: hidden test 4 failed: got 20.0, expected 0.0
bugfix:average-rating   schema: not exactly one JSON object (Expecting value at character 0)
                        schema: valid only under the lenient parse (a format problem)
                        exec: not run (the answer is not schema-valid)
bugfix:evaluate-sum     sast block: eval-exec: eval(expression)
                        exec: not run (block-class finding: eval-exec)
```

The first is an overfit (its shown test passed), the second a format failure, and the third a
patch that was never run.

## Recording new cassettes against a live endpoint

The harness talks to any OpenAI-compatible chat-completions endpoint (vLLM, llama.cpp's server, a
hosted API) over `urllib`. There is no SDK dependency.

```bash
export LLM_EVAL_BASE_URL=http://localhost:8000/v1
export LLM_EVAL_API_KEY=...            # read from the environment only; never put it in a file or a flag

# 1. Record both features into one new cassette directory (all splits by default, so the
#    held-out gate can run later). Re-running the same command resumes an interrupted recording.
llm-eval record --feature bugfix --model my-model --out cassettes/my-model
llm-eval record --feature judge  --model my-model --out cassettes/my-model

# 2. Iterate on dev as often as you like.
llm-eval run --feature bugfix --cassettes cassettes/my-model --split dev

# 3. Gate it once against the current baseline on the held-out split.
llm-eval gate --feature bugfix --candidate cassettes/my-model --baseline @current > report.json
```

What recording does and refuses:

- Each request is the one replay will rebuild: the template, the model name and the settings
  (temperature 0, a fixed seed and the feature's `max_tokens` by default) are stored in the
  directory's `manifest.json`, and each answer is stored with its request's sha256. A recording is
  replayed only for the exact request it answered.
- A request that still fails after the client's retries is not recorded, and the command exits 1.
  (`--max-retries` retries connection errors, timeouts and the statuses 408, 409, 425, 429, 500,
  502, 503 and 504, with backoff and the server's `Retry-After`.) A failure is never stored as an
  empty answer, which would score a flaky endpoint as a bad model. Run the same command again to
  resume.
- Recording a feature into a directory whose recordings of that feature used another model,
  prompt, settings or suite version is refused: record into a new directory. Different features
  can share a directory, as above.
- `--prompt bugfix/v1` records another template, and `--prompt-from DIR` copies the template and
  settings another cassette set used. `--temperature`, `--max-tokens`, `--seed` (or `--seed none`)
  and `--extra '{"chat_template_kwargs": {"enable_thinking": true}}'` change the request.
  `--api-key-env VAR` reads the key from another variable.
- Thinking that the server returns separately (`reasoning_content` or `reasoning`) is scored like a
  `<think>` block.

Then:

1. **Open a pull request with the cassettes.** CI gates `cassettes/candidate`. Either record into
   that directory in place of the synthetic candidate, or change that path in the `regression-gate`
   job. CI then replays your recordings: free, deterministic, and with no secrets.
2. **Promote after review.** After merging, make the recording the baseline in a reviewed commit:
   `llm-eval ledger promote --feature bugfix --to cassettes/my-model --report report.json --reason "..."`.
   The promotion is refused if the report is not a passing held-out report of this candidate
   against the current baseline. If a promoted baseline misbehaves later,
   `llm-eval ledger rollback --feature bugfix --reason "..."` restores the previous one.
3. **Watch the held-out budget.** `llm-eval gate --record-evaluation` notes each held-out run in
   the ledger. Once 10 distinct candidates have been judged on the split, every report warns that
   the split is spent and needs fresh tasks. CI never writes the ledger.

A new prompt is a new template version (`bugfix/v3` in `prompts.TEMPLATES`). Published templates
never change, because every recording is replayed only for the exact request it answered. To
change the demo itself, see [Changing the demo](#changing-the-demo).

## The sandbox is not a security boundary

Model-written code runs in a sandbox:

- a fresh temporary directory (working directory, `HOME` and `TMPDIR`), removed afterwards;
- a child process started as `python -I -S`, with an environment built from scratch (nothing is
  inherited, so no API key reaches it);
- a deadline (10 s per item by default), after which the whole process group is killed;
- best-effort limits on CPU time, memory and file size.

This keeps a careless or overfitted patch away from your working tree, your secrets and the
verdict. **It does not stop a hostile patch:** the child runs as your user, can read your files and
can open network connections, and a process that leaves its process group escapes the kill. In CI,
the only code executed is the code in the committed cassettes, reviewed in the pull request like
any other file, on a throwaway runner without secrets. Score an untrusted model's recordings inside
a container or VM without network access. Recording needs the network; scoring does not:

```bash
docker run --rm --network none -v "$PWD":/repo:ro -w /repo -e PYTHONPATH=src -e PYTHONDONTWRITEBYTECODE=1 \
  python:3.12-slim python -m llm_eval_harness gate --feature bugfix --candidate cassettes/my-model --baseline @current
```

The sandbox is POSIX-only, and macOS usually refuses its memory limit, which is then skipped. It
has been tested on Linux; CI runs it on Ubuntu. The static scan narrows
what a patch can do unseen, but it does not close every gap: a name built at run time is invisible
to it.

## Limitations

- **Synthetic demo.** The cassettes show the mechanics, not the quality of any model. Their token
  counts are estimates (characters / 4).
- **Small suite.** 21 held-out tasks detect only large regressions (see `mde80` and
  `min_significant_losses` in every report). The demo holds out about half its tasks
  (`heldout_pct` 50; the hash put 21 of 34 there) so that the held-out split can detect anything at
  all. Larger suites should hold out a smaller share.
- **Public held-out split.** It is held out from prompt tuning, not from the internet: a model
  trained on this repository has seen it. A real deployment keeps its held-out suite private
  (`--suite` can point anywhere). Items files and reports quote hidden-test values in their
  problem lines, so keep them as private as the suite.
- **Toy tasks.** The tasks are small pure functions. Real bug fixing spans files and repositories
  with their own test environments. The harness's structure carries over; its sandbox does not.
- **One sample per item.** A recording is one answer per item. A live endpoint is not
  deterministic even at temperature 0, so for noisy comparisons set a `--margin`.
- **Narrow judge evaluation.** The judge is evaluated on exactly two patches per task: the
  reference fix and the overfitted one.

## Changing the demo

The cassettes answer requests built from the task file and the prompt templates, and the ledger
holds the baseline's fingerprint, so they change together:

```bash
llm-eval tasks validate --suite tasks/demo        # after editing tasks/demo/tasks.jsonl
python scripts/make_demo_cassettes.py             # regenerate the three synthetic sets
rm ledger/ledger.jsonl                            # the baseline's fingerprint changed: restart the ledger
llm-eval ledger promote --feature bugfix --to cassettes/baseline --initial --reason "initial baseline (synthetic demo)"
llm-eval ledger promote --feature judge  --to cassettes/baseline --initial --reason "initial baseline (synthetic demo)"
python scripts/make_demo_cassettes.py --check     # what tests/test_demo.py checks
```

`tests/test_demo.py` pins the demo's numbers, and this README and `docs/DESIGN.md` quote them:
update all three together. Once real recordings replace the synthetic sets, the demo has done its
job, so update or drop its pinned values in the same pull request.

## Origin

This harness was extracted from a larger project that trains a multi-agent coding team, and
rewritten small and standalone for this repository. It shares no code or data with that project.
The design choices come from building that project's promotion gate:

- **A tie is a decision, so the gate rule names it.** "Candidate >= baseline" silently promotes
  changes that do nothing.
- **Every look at the held-out split spends it.** Iterate on dev; the ledger counts held-out
  evaluations.
- **Split on stable ids, not on text,** and keep twins on one side, or editing a task leaks it.
- **Exit status 0 is not a pass.** Compare values in a process the model's code does not control,
  and never let an infrastructure fault become a verdict.
- **An LLM judge can sit at chance while sounding sure.** Measure it against execution labels, and
  accept patches on tests plus a static scan, not on a judge's word.
- **A report should say how large a change its suite can detect.**

[docs/DESIGN.md](docs/DESIGN.md), section 13, explains each one.
