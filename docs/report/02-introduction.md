# I. Introduction

## A. Problem

Software teams increasingly ship features whose behaviour is produced by an LLM: a prompt template, a model, optional adapters and a serving configuration together determine the output. Each of these is changed routinely. A prompt is reworded, a model is replaced by a newer release, a parameter-efficient adapter is trained [1], weights are quantized to fit cheaper hardware [2], [3], or the serving engine is replaced [4], [5]. None of these changes touches the code that unit tests exercise, yet any of them can make the feature worse. The question that a regression test must answer for such a change is therefore not whether the code is correct, but whether the change makes the feature worse on inputs it was not tuned on, and how confident that answer can be.

Benchmarks for code generation answer a related but different question: how good a model is, on average, on a public task set [6], [7], [8]. A regression gate instead compares two configurations of one product feature, decides whether the second may replace the first, and must make that decision automatically, reproducibly and cheaply on every change, typically in CI, where calling a 27-billion-parameter model is neither free nor deterministic.

## B. Motivation

Three observations motivate a dedicated harness. First, the comparison is between two arms on the same items, so a paired analysis is available and much stronger than comparing two aggregate scores [9], [10]. Second, the suites a product team can afford to label with executable tests are small, tens to hundreds of items, and on such suites statistical power is low [11]; a gate that does not state how large a change it could detect invites over-interpretation of both its passes and its failures. Third, the decision rule must be explicit about ties. A rule of the form "candidate >= baseline" promotes every change that does nothing, and a rule that demands significance rejects nearly every candidate on a small suite. Non-inferiority testing, as used in clinical trials [12], makes the margin and the direction of the burden of proof explicit, and the same discipline applies here.

LLM-specific failure modes add requirements. A reply can be malformed, truncated at the token limit, or correct only on the test the model was shown. Generated code can call `eval` or spawn processes, and a judge or reviewer model can approve wrong patches while sounding confident [13]. Serving is nondeterministic even at temperature zero [14], [15], so two recordings of the same configuration can differ, and uncapped reasoning budgets can induce length truncation that confounds downstream capability measurements with formatting failures.

## C. Contributions

This report makes the following contributions, each implemented and tested in the accompanying repository:

1. **A paired non-inferiority gate across four LLM features** (rule `noninferior/1`, `src/llm_eval_harness/gate.py`) spanning single-function bug fixing (`bugfix`), patch-correctness judging (`judge`), pull-request diff review (`review`), and multi-file unified diff patching (`patch`), with an explicit margin and tie policy, hard validity gates, a new-SAST gate, an exact McNemar guard [16], and reported detection limits ($\mathrm{MDE}_{80}$ and minimum significant losses).
2. **Execution-grounded scoring and safe patch verification** (`verdicts.py`, `sandbox.py`, `sast.py`, `diff_apply.py`) in which tests are stored as data, the child process returns only values while the parent judges them, shown and hidden tests separate genuine fixes from overfitting, and a pure-Python unified-diff applier with `--recount` semantics verifies multi-file patches alongside an AST/regex static scan.
3. **Execution-labelled judge and review evaluation** where `judge` pairs one correct and one plausible wrong patch per task (0.5 chance baseline) and `review` scales classifier gating to non-ceiling real pull-request diffs, accompanied by the post-hoc `both_valid_compare` decomposition isolating pure discrimination from formatting failures.
4. **Deterministic request-addressed cassettes and hash-chained ledger** (`cassettes.py`, `clients.py`, `ledger.py`): replies in plain `.jsonl` or deterministic gzip `.jsonl.gz` (`mtime=0`) are keyed by the SHA-256 of the exact request body and replayed offline in CI alongside a self-test regressed arm and a hash-chained promotion/rollback ledger tracking held-out split exhaustion.
5. **Empirical characterization from ceiling noise to non-ceiling real-repository effects (Experiments A–D)** on 27B open-weight models, demonstrating why `demo` and `humanevalfix` mask small capability differences inside serving noise ($\pm 0.041$) while real-repository suites (`swe_review_bench`, $n=400$; `swe_coder_effort`, $n=297$) cleanly isolate genuine adaptation gains ($+0.188$ BA, $+0.089$ mutually valid) and massive reasoning-effort effects ($+0.391$ held-out usable rate, $5.02\times$ pooled token savings).
6. **Agentic harness feature ablations and confound analysis**, showing how uncapped serving baselines mask a $-0.040$ security capability regression behind a $+0.048$ format lift, how read-only test context plus plan revision lifts first-attempt MBPP verification from 9.5% to 88.0%, and how replacing LLM auditor vetoes with deterministic `tests+SAST` gating eliminates 34.8% false rejections with 0 false accepts and $7.0\times$ lower token cost per resolved task.
