# IV. Experimental Methodology

## A. Task suites and splits

**Demo suite.** `tasks/demo` holds 34 tasks written for the repository and taken from no dataset or code base (`"synthetic": true` in `suite.json`). Each task is a small pure Python function with one bug, tagged by bug class (`off-by-one`, `boundary` and others), one shown test that fails on the buggy code, at least two hidden tests, a reference fix and a plausible wrong fix. `llm-eval tasks validate`, run by CI on every Python version, checks in the sandbox that the buggy code fails its shown test, that the reference passes every test twice with the same outcomes, that the wrong fix passes the shown test and fails a hidden one, that no block-class rule fires on any of the three code fields, and that no rendered prompt contains a hidden test's call, the reference or the wrong fix.

**Split.** A task's split is a deterministic function of a stable key, never of its text:

$$ \mathrm{bucket} = \mathrm{int}\big(\mathrm{sha256}(\mathrm{key})[0{:}8],\,16\big) \bmod 100, $$

where the key is the task's normalised `group` or, without one, its identifier, and the task is held out when the bucket is below the suite's `heldout_pct`. Editing a task's wording therefore never moves it across the split, and adding a task never moves another. Twins, tasks that pose the same problem reworded or with a renamed function, share a group and therefore a side; `tasks.find_twins` warns about near-identical code across the split and validation fails on identical code. The demo suite sets `heldout_pct` to 50 so that its held-out split is large enough to detect anything at all; the hash places 21 tasks (20 clusters, because `digit-sum` and `sum-of-digits` are twins) in the held-out split and 13 in the dev split. The bug-fix feature thus has 21 held-out and 13 dev items, and the judge 42 and 26.

**HumanEvalFix suite (Experiment C).** Experiment C uses the Python problems of HumanEvalFix [17], whose buggy functions derive from HumanEval [6], converted to the harness's suite format by `scripts/import_humanevalfix.py` into `tasks/humanevalfix/`. The suite's `README.md` and `IMPORT.json` document each conversion choice and every task or assertion the format cannot express exactly and that is therefore left out. 115 of the 164 problems are kept. The model is shown the buggy function and the docstring's examples as tests (median 2 per task), and the remaining expressible asserts of the full test are hidden (median 4, range 2 to 25). With `heldout_pct` 60 the same hash split places 74 tasks in the held-out split and 41 in the dev split, so the bug fix has 74 and 41 items and the judge 148 and 82. The judge's wrong patch for each task is the buggy solution behind a guard that returns the expected value of each shown test for exactly that test's arguments, so that it passes the shown tests and fails a hidden one. Scores on this suite are not comparable with published HumanEvalFix results, which show the model the full tests and score pass@k on 164 problems.

## B. Arms

**Controlled synthetic arms.** `cassettes/baseline`, `cassettes/candidate` and `cassettes/candidate-regressed` were generated by `scripts/make_demo_cassettes.py`, not by a model, from documented deterministic rules over each task's position in its split: the reference code stands for a fix, the wrong code for an overfitted patch, and hand-written `eval()` variants, prose around the JSON, a missing key and replies truncated at the token limit stand for the failures. The baseline uses prompts `bugfix/v1` and `judge/v1`; the candidate uses `v2`, which adds the instruction to fix the function for every input its docstring describes and not to special-case test inputs; the regressed candidate uses `v2` with a nominally smaller model. These arms have known ground truth by construction and test the gate, not any model.

**Experiment A: LoRA adapters on an open-weight model** (`experiments/exp-a-qwen38/`). The base model is Qwen3.8-27B [32], in a community fine-tune whose refusal behaviour was removed by "abliteration", a weight edit along the refusal direction identified by Arditi et al. [34], in bf16, served by vLLM [4] on two A100 GPUs with thinking enabled (the series' thinking mode is described in [35]). Two arms were recorded on the same server:

- `qwen38-base`: the base model for both features (served model name `qwen38`).
- `qwen38-adapters`: for the bug fix, an *identity* LoRA adapter [1] of rank 64 whose `lora_B` matrices are all zero, so that the adapted model equals the base model in exact arithmetic (served name `coder-lora`); for the judge, a *trained* LoRA adapter of rank 64, trained on the base model's own rejection-sampled verdicts on public code-review data (served name `judge-lora`).

Both arms used prompts `bugfix/v2` and `judge/v2`. The identity adapter is a no-op control: any difference it produces measures the serving stack, not the adapter.

**Experiment C: weight quantization and serving engine** (`experiments/exp-c-bonsai/`). Four arms were recorded for both features on the HumanEvalFix suite:

- `bf16-vllm`: the stock Qwen3.8-27B [32] in bf16, served by vLLM [4].
- `bf16-vllm-rerun`: the same model, engine and settings, recorded a second time. It is the no-op control of this experiment: any difference it produces measures the serving stack's run-to-run variation.
- `q8-llamacpp`: the stock Qwen3.8-27B converted to a Q8_0 GGUF file and served by llama.cpp [5] (release b12682), the engine control.
- `ternary-llamacpp`: Ternary Bonsai 2 27B [31], a ternary model with Qwen3.8-27B as its base, as its published Q2_0 GGUF file (the packing that runs on stock llama.cpp), served by the same llama.cpp release.

Four paired comparisons follow: C0, the rerun against bf16, measures the noise floor; C1, Q8_0 against bf16, measures the change of engine (together with 8-bit rounding, expected to be small); C2, ternary against Q8_0, measures the ternary model at a fixed engine; and C3, ternary against bf16, measures the whole deployment change, as a product team would experience it. Without the control arm, C3 alone could not separate the effect of the weights from that of the engine. Every arm was served under the model name `qwen38`, so the arm, not the reported model name, identifies the weights and the engine. The bf16, Q8_0 and ternary arms were also recorded on the demo suite (`experiments/exp-c-bonsai-demo/`, comparisons C1 to C3), without a rerun arm.

## C. Recording protocol

Replies are recorded with `llm-eval record`, which builds each item's request exactly as replay will rebuild it and stores the model name, prompt identifier and settings in the cassette directory's `manifest.json`, and each reply under its request's SHA-256. Experiment A used temperature 0, seed 0, at most 16,384 completion tokens and `{"chat_template_kwargs": {"enable_thinking": true}}` (`experiments/exp-a-qwen38/*/manifest.json`). The server returned the thinking in a separate reasoning field, which the harness scores like a `<think>` block. A request that fails after the client's retries is not recorded, so an unreliable endpoint cannot be scored as a bad model; re-running the command resumes. Recording into a directory whose recordings of the same feature used a different model, prompt, settings or suite version is refused. Experiment C used the same settings for every arm, with `reasoning_effort` set to `medium` in the same `chat_template_kwargs` (`experiments/exp-c-*/*/manifest.json`). Medium effort follows the publisher's known-issues page for the ternary model, which recommends it against long reasoning and loops at output limits around 16,000 tokens [31]; the publisher's recommended sampling settings (temperature 1.0 and others) were not used, so that every arm decodes greedily. Both engines returned the thinking in the separate reasoning field. Each arm holds one reply per item: the experiments sample once at temperature 0.

## D. Replay determinism

Replay rebuilds every request from the manifest and the suite and compares its SHA-256 with the recorded one; a mismatch or a missing recording refuses the evaluation. The bootstrap is seeded per feature and split, and the report is serialised canonically without time stamps, host names or absolute paths. Replaying the same cassettes therefore yields the same bytes on any machine. Every experiment's committed reports are in `experiments/<experiment>/expected/`, one per comparison, feature and split, produced by

```text
llm-eval gate --suite tasks/<suite> \
  --feature <f> --split <s> \
  --candidate experiments/<exp>/<candidate> \
  --baseline experiments/<exp>/<baseline>
```

with the default gate configuration (margin 0, ties pass, schema validity at least 0.95, thinking validity at least 0.90, alpha 0.05, 2,000 bootstrap draws, seed 0). A report named `<candidate>--vs--<baseline>.<feature>-<split>.json` names its two arm directories; Experiment A's four reports keep the earlier names `<feature>-<split>.json`, with candidate `qwen38-adapters` and baseline `qwen38-base`. The suite is the one named in the experiment's `SUITE` file (`humanevalfix` for `exp-c-bonsai`, `demo` otherwise). The CI job `experiments` reruns these commands for all 32 committed reports (4 of Experiment A, 16 of Experiment C and 12 of its demo-suite replication) and compares each output with the committed file using `cmp`.

## E. Hypotheses

The following hypotheses state what the design of each arm predicts. They are listed before any result. H1 and H2 follow from the harness's specification; H3 and H4 state what the adapters were expected to do, and were written down in this form after Experiment A's replies had been recorded (Section VI-E). H5 and H6 were stated in the plan for Experiment C, for the bug-fix feature and the three arms bf16, Q8_0 and ternary, before it was recorded. That plan is not among the repository's files, so the order cannot be checked from them, and it fixed no margin.

- **H1 (gate validity on controlled arms).** On the held-out demo split, the synthetic candidate promotes for both features, and the synthetic regressed candidate is rejected, failing at least `primary`, `schema_validity` and `new_sast_violations` for the bug fix and `primary` and `schema_validity` for the judge.
- **H2 (replay determinism).** Replaying the committed cassettes with the committed harness reproduces every committed report byte for byte.
- **H3 (no-op invariance).** The identity adapter's bug-fix replies equal the base model's on every item, so that $\Delta = 0$ with no gains and no losses on both splits, and the gate promotes under the default tie policy.
- **H4 (trained judge).** The trained judge adapter raises balanced accuracy over the base model ($\Delta > 0$) on both splits and is promoted on both.
- **H5 (engine control, Experiment C).** Comparison C1 (Q8_0 under llama.cpp against bf16 under vLLM) is not rejected by `regression_test`, and its number of discordant items is of the same order as the no-op discordance measured in Experiment A.
- **H6 (ternary weights, Experiment C).** Comparison C2 (ternary against Q8_0, both under llama.cpp) is promoted by rule `noninferior/1`.

Because the plan fixed no margin, H6 is tested at the gate's default, margin 0 with ties passing, the configuration of the committed reports. Four parts of Experiment C have no hypothesis and are reported as exploratory: the rerun arm and comparison C0, the judge feature, the replication on the demo suite, and the retention ratio of the ternary model.

## F. Analysis plan

Each report is one decision and is interpreted on its own; no correction for multiple comparisons is applied, and Section VI discusses the consequence. Every decision is read together with its interval, $\mathrm{MDE}_{80}$ and the number of discordant items. For every discordant item of Experiment A and of Experiment C's HumanEvalFix comparisons, the per-item rows written by `llm-eval gate --items-out DIR` are inspected to classify the disagreement as a functional failure (a test failed or a verdict was wrong) or a format failure (truncation, invalid thinking, or a reply that is not a strictly valid JSON object). Cost is reported as mean completion tokens per item and median latency, and is not gated.
