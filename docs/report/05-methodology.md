# IV. Experimental Methodology

## A. Task suites and deterministic splits

Every suite assigns items deterministically without state by hashing a normalized cluster key (task `group`, or `id` if ungrouped):

$$\mathrm{bucket} = \mathrm{int}\big(\mathrm{sha256}(\mathrm{key})[0{:}8],\,16\big) \bmod 100,$$

placing tasks with $\mathrm{bucket} < \mathrm{heldout\_pct}$ in `heldout` and the remainder in `dev`. Four suites reside in `tasks/`:

- **`tasks/demo`** (`"kind": "function"`, `"synthetic": true`, `heldout_pct: 50`): 34 synthetic pure-Python single-function bug-fix tasks yielding 21 `heldout` (20 clusters due to twin pair `digit-sum`/`sum-of-digits`) and 13 `dev` items for `bugfix`, and 42 / 26 items for `judge`.
- **`tasks/humanevalfix`** (`"kind": "function"`, `heldout_pct: 60`): 115 converted Python HumanEvalFix [17] tasks (from 164 [6], omitting unexpressible assertions), keeping docstring examples as shown tests (median 2) and remaining asserts hidden (median 4), yielding 74 `heldout` / 41 `dev` `bugfix` items and 148 / 82 `judge` items.
- **`tasks/swe_review_bench`** (`"kind": "review"`, `tasks.jsonl.gz`, `heldout_pct: 50`): 400 real pull-request review items from Apache-2.0 `Lego-X/SWE-Review-Bench` across 12 external Python repositories unseen during training, clustered by normalized PR instance into 302 clusters: 183 `heldout` (143 PR clusters) and 217 `dev` (159 PR clusters), with execution-derived pass/fail labels.
- **`tasks/swe_coder_effort`** (`"kind": "patch"`, `tasks.jsonl.gz`, `heldout_pct: 50`): multi-file repository patching tasks from CC-BY-4.0 `nvidia/Nemotron-Cascade-RL-SWE` across 65 repository clusters. From 300 source candidates, suite validation dropped 3 tasks whose reference `gold_files` triggered block-class SAST rules (`interpreter-tamper` or `unsafe-deserialization`), retaining $n=297$ tasks split cleanly by repository into 169 `heldout` (35 repo clusters) and 128 `dev` (30 repo clusters).

## B. Base weights, model arms, and attribution

We explicitly distinguish the base weights and serving configurations across the four harness experiments:

**Synthetic gate validation (`cassettes/`).** Three deterministic rule-generated arms (`baseline` on `v1`, `candidate` on `v2`, and `candidate-regressed` with injected `eval()`, malformed JSON, and length truncation) validate gate mechanics offline.

**Experiments A, B, and D: Abliterated Qwen3.8-27B base.** These three experiments evaluate `Huihui-Qwen3.8-27B-abliterated` (refusal direction ablated per Arditi et al. [34]) derived from Qwen3.8-27B [32], [35] and served in bf16 with uncapped thinking:

- **Experiment A (`exp-a-qwen38`, `demo`):** Compares `qwen38-base` against `qwen38-adapters` using two rank-64 LoRA [1] adapters under vLLM [4]: an arithmetic-identity `coder-lora` (`lora_B=0`) on `bugfix/v2`, and a trained `judge-lora` on `judge/v2`.
- **Experiment B (`exp-b-review-lora`, `swe_review_bench`):** Compares uncapped `xhigh` `qwen38-base` against `qwen38-review-lora` (served as `public-v2-review`, an SFT LoRA trained with thinking-window calibration capped at 700 words during data curation, `w700`; manifest metadata records `r=32, alpha=64`) on `review/v1`.
- **Experiment D (`exp-d-coder-effort`, `swe_coder_effort`):** Compares three uncapped reasoning-effort configurations of `qwen38-base` on `patch/v1`: `effort-xhigh`, `effort-medium`, and `effort-low` across D1 (`medium` vs. `xhigh`), D2 (`low` vs. `xhigh`), and D3 (`low` vs. `medium`).

**Llama 3.1 Attribution Notice.** In connection with Experiment A and our sibling public-track adapters: while Experiment B trains on Apache-2.0 (`Lego-X/SWE-Review-Traj`) and CC-BY-4.0 (`nvidia/Open-SWE-Traces`) sources, our public judge SFT pipeline (`public-v2-judge`) distills verdicts over agent patches generated by open-weight Llama models (`nebius/SWE-agent-trajectories`, `swe-agent-llama-8b/70b/405b`). Published derivatives of those Llama-output traces carry the required "Built with Llama" notice under the Llama 3.1 Community License.

**Experiment C: Stock Qwen3.8-27B vs. 2-bit Ternary Bonsai 2 (`exp-c-bonsai`, `-demo`).** Experiment C uses stock `Qwen/Qwen3.8-27B` [32] at `reasoning_effort=medium` across four arms on `humanevalfix` (and three on `demo`): `bf16-vllm` (stock bf16 on vLLM), `bf16-vllm-rerun` (C0 no-op noise floor), `q8-llamacpp` (stock Q8_0 GGUF on `llama.cpp` b12682, C1 engine control), and `ternary-llamacpp` (Ternary Bonsai 2 27B Q2_0 GGUF [31] on `llama.cpp`, yielding C2 fixed-engine ternary and C3 full deployment comparison).

## C. Recording protocol and replay determinism

All arms were recorded via OpenAI-compatible serving endpoints with separately returned reasoning fields and verified in CI without GPU access. Experiment A used temperature 0.0, seed 0, `max_tokens=16384`, and `enable_thinking=true`; Experiment B used temperature 0.0, `top_p=0.95`, `top_k=20`, `presence_penalty=0.0`, `max_tokens=16384`, and uncapped `xhigh`; Experiment C used temperature 0.0, seed 0, `max_tokens=16384`, and `reasoning_effort=medium` per Bonsai 2 guidance [31]; Experiment D used temperature 0.1, `top_p=0.95`, `top_k=20`, `max_tokens=32768`, and single-sample (`sample=0`) decoding across `xhigh`/`medium`/`low`. Replaying the 40 committed gate reports (`exp-a`: 4, `exp-b`: 2, `exp-c`: 16, `exp-c-demo`: 12, `exp-d`: 6) reproduces identical bytes under `cmp`.

## D. Agentic harness feature ablations

To connect single-turn CI gating with full multi-agent deployment dynamics, we evaluate three complementary harness ablations on repository-disjoint and multi-agent rollout suites: (1) a **budget-forcing confound control** on $n=396$ security vulnerability classification items (128 repo clusters from PrimeVul and VulMine, temperature 0.0, 16,384 tokens) comparing a trained SFT security LoRA against both uncapped `qwen38-base` and a paragraph-capped base control (`think_budget=1300`, `think_max_words=700`); (2) **test visibility and plan revision** comparing baseline MBPP agent rollouts ($n=814$) against read-only test context plus failure-triggered replanning ($n=299$ pre-exclusion / $n=295$ post-exclusion MBPP rollouts); and (3) **deterministic `tests+SAST` gating vs. LLM auditor veto** paired on $n=50$ real-repository tasks in a 5-agent coding team (orchestrator, coder, review, security, judge).

## E. Hypotheses and pre-specified vs. post-hoc separation

Pre-specified gate rules (`noninferior/1`: margin 0, `--tie pass`, schema $\ge 0.95$, think $\ge 0.90$, new block SAST $\le 0$, McNemar $\alpha=0.05$) govern every promotion verdict prior to outcome inspection. Hypotheses H1–H8 test: **H1** synthetic gate validity; **H2** byte-identical replay determinism; **H3** arithmetic-identity LoRA non-inferiority; **H4** trained judge gain; **H5** C1 engine-control invariance; **H6** C2 ternary non-inferiority; **H7** Experiment B `w700` review LoRA superiority on `swe_review_bench`; and **H8** Experiment D effort reduction from `xhigh` to `medium`/`low` recovering usability without losing quality relative to `medium` vs. `low`. Post-hoc diagnostic analyses—explicitly separated from promotion verdicts—include `both_valid_compare`, per-item format vs. functional classification, C0 exploration, and the margin 0.05 sensitivity reading.
