# II. Related Work

## A. Execution-based evaluation of code generation

HumanEval [6] established functional correctness, measured by executing unit tests, as the standard for evaluating generated code, and MBPP [7] provided a larger set of entry-level Python problems with test cases. HumanEvalPack [17] extended HumanEval to code repair, explanation and synthesis in six languages; its repair task, HumanEvalFix, gives the model a function with an inserted bug and is the task family closest to the bug-fix feature evaluated here. SWE-bench [8] moved evaluation to real repositories, with issues and pull requests from popular Python projects. EvalPlus [18] showed that the original HumanEval tests miss a substantial share of wrong programs, and that adding generated tests lowers reported pass rates. The present harness adopts the same lesson at small scale: every task has hidden tests beyond the one shown to the model, and a patch that passes the shown test but fails a hidden one is counted separately as an overfit. Unlike these benchmarks, the harness is not designed to rank models in general; it compares two configurations of one feature and decides whether one may replace the other.

## B. Contamination and the reuse of held-out data

Public benchmarks may be part of a model's training data. Sainz et al. [19] argue that contamination must be measured per benchmark, and LiveCodeBench [20] addresses it by evaluating only on problems published after a model's training cut-off. A second, subtler form of leakage arises from the evaluator's own decisions: each time a held-out set is used to choose between candidates, information about it flows into the choice. Dwork et al. [21] formalise this adaptive reuse of a holdout and propose mechanisms that preserve validity, and Recht et al. [22], who rebuilt the CIFAR-10 and ImageNet test sets, found accuracy drops of 3% to 15% and 11% to 14% on the new sets, which they attribute to slightly harder images rather than to adaptive overfitting; a reused test set is thus not necessarily spent, but whether it is can only be established with fresh data. The harness splits tasks by a hash of a stable key rather than of their text, keeps near-duplicate "twin" tasks on one side of the split, and its ledger counts the distinct candidates evaluated on the held-out split and warns once a budget is spent.

## C. LLMs as judges

Zheng et al. [13] found that strong LLM judges agree with human preferences at rates comparable to inter-human agreement, while documenting position, verbosity and self-enhancement biases. For code, a judge's opinion can be checked against execution. The judge feature of this harness is evaluated only against labels obtained by running tests, on a design in which every task contributes one correct and one wrong patch, so that balanced accuracy separates a judge that reads the patch from one that does not.

## D. Statistical comparison of models

McNemar's test [16] compares two classifiers evaluated on the same items using only the items on which they disagree; Dietterich [9] found it to have low type I error among tests for comparing learning algorithms. Paired bootstrap resampling [23] is the standard way to attach confidence intervals to differences in evaluation metrics [24], and Dror et al. [25] give a protocol for choosing among significance tests in natural language processing. Card et al. [11] showed that many comparisons in that field are underpowered, and Miller [10] treats an evaluation as an experiment on questions drawn from a super-population, recommends reporting standard errors, clustered when questions are not independent, and gives formulas for comparing two models and for planning an evaluation's size. The Wilson score interval [26] keeps binomial intervals inside [0, 1] and performs well at small sample sizes [27]. The harness combines these elements: Wilson intervals for rates, a paired cluster bootstrap for the difference, an exact McNemar test on the discordant items, and a minimum detectable effect in every report. Its decision rule follows the logic of non-inferiority testing [12], with the margin, the tie policy and the optional requirement of a significant gain made explicit.

## E. Testing machine-learning systems

Breck et al. [28] propose 28 specific tests and monitoring needs as a rubric for the production readiness of machine-learning systems, observing that such tests are hard to write because a model's behaviour is hard to specify in advance. CheckList [29] brings behavioural testing from software engineering to natural language processing models. The harness applies the regression-testing part of this agenda to an LLM feature and runs it in CI. To make CI deterministic and free of model calls, it records model replies and replays them, in the manner of HTTP record-and-replay test libraries such as VCR.py [30], but keys each recording to the SHA-256 of the full request, so that a changed prompt, model name or sampling setting invalidates the recording instead of silently reusing it.

## F. Adaptation, quantization and serving

LoRA [1] adapts a frozen model by training low-rank update matrices; with the update's second factor initialised to zero, an adapter is an exact identity, which Experiment A uses as a no-op control. Post-training quantization such as GPTQ [2] reduces weights to 3 or 4 bits with little loss, and BitNet b1.58 [3] trains models whose weights are ternary, {-1, 0, +1}, from scratch. Ternary Bonsai 2 [31] is a ternary model published with Qwen3.8-27B [32] as its base model and distributed as GGUF files for llama.cpp [5]; Experiment C compares it with the bf16 model. vLLM [4] serves models with paged key-value memory and continuous batching, and speculative decoding [33] accelerates generation without changing the output distribution in exact arithmetic. In floating point, however, results depend on batch composition and reduction order: Yuan et al. [14] report accuracy differences of up to 9% for a reasoning model under greedy decoding in bfloat16 as the GPU count, GPU type and batch size change, and He et al. [15] attribute most run-to-run variation of inference servers to kernels that are not invariant to batch size. Experiment A measures the consequence for a regression gate directly.
